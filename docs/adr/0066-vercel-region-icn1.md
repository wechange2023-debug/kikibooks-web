## Context

### 1. 실행 지역이 미국이고, DB는 서울이다

P-0에서 배포본 응답 헤더를 채집했다.

```
$ curl -I https://www.hellokiki.co.kr/
X-Vercel-Id: icn1::iad1::qtdc2-1787363595368-b2ad71635398
```

가운데 토큰이 **함수 실행 지역**이다. `iad1`은 미국 워싱턴 D.C.다. 앞의 `icn1`은 요청을
받은 엣지 PoP(서울)이므로, **한국 사용자가 서울 엣지에 닿은 뒤 버지니아까지 왕복**한다.

지역을 지정한 곳이 저장소에 **한 군데도 없었다** — `vercel.json`·`vercel.ts` 부재,
`next.config.js`에 `regions` 0건, 전 라우트에 `preferredRegion` 0건. 즉 `iad1`은
누가 고른 값이 아니라 Vercel 기본값이다.

한편 Supabase 인스턴스는 **서울(`ap-northeast-2`)** 이다. 지시서가 준 값을 워커가 재검산했다 —
`db.<project-ref>.supabase.co`가 **`2406:da12:…`** 로 해소되며, `2406:da12::/32`는 AWS
`ap-northeast-2` 대역이다. (`<project-ref>.supabase.co` 쪽은 Cloudflare가 앞에 있어
`CF-RAY … -ICN`이 찍히지만 그것은 **조회자 위치**를 뜻하므로 근거로 쓰지 않았다.)
아래 §2의 로컬 제품 모드 수치도 같은 방향이다 — 서울에서 4단 왕복하는 책 상세가 207 ms에
끝나는 것은 DB가 가까울 때만 가능하다.

즉 **데이터가 서울에 있는데 그 데이터를 읽는 함수가 버지니아에서 돈다.**

### 2. 실측 — 같은 코드가 5.9~10.4배 차이 난다

P-0 표 1. 배포본(함수 `iad1`)과 로컬 제품 모드(`next start`, 같은 빌드, 서울에서 서울 DB
조회)를 같은 방법·같은 책 id·로그인 상태·3회 중앙값으로 쟀다.

**(A) 문서 응답 완료까지**

| 화면 | 로컬 제품(서울) | 배포본(iad1) | 배수 |
|---|---|---|---|
| `/` 메인 | 514 ms | **3,518 ms** | 6.8× |
| `/library` | 293 ms | **2,098 ms** | 7.2× |
| `/mypage` | 383 ms | **3,433 ms** | 9.0× |
| `/book/{id}` 상세 | 207 ms | **2,161 ms** | 10.4× |
| `/book/{id}/read` | 317 ms | **2,081 ms** | 6.6× |

**(C) 클라이언트 라우팅(Link 클릭 시 발생하는 RSC 페이로드)**

| 화면 | 로컬 제품(서울) | 배포본(iad1) | 배수 |
|---|---|---|---|
| `/` | 363 ms | **3,168 ms** | 8.7× |
| `/library` | 261 ms | **1,536 ms** | 5.9× |
| `/mypage` | 385 ms | **2,321 ms** | 6.0× |
| `/book/{id}` | 176 ms | **1,168 ms** | 6.6× |
| `/read` | 315 ms | **2,253 ms** | 7.2× |

페이로드 크기는 두 환경이 거의 같다(예: `/` 28.6 KB ↔ 28.8 KB). **전송량이 아니라 대기
시간**이 갈린 것이다.

### 3. 이 값이 왜 커지는가 — 왕복이 여러 번이다

P-0 표 3(d) 실측. 화면 하나를 그리는 데 Supabase 왕복이 **순차로** 쌓인다.

| 화면 | 순차 단계 | 파일:라인 |
|---|---|---|
| `/` | 3단 | `app/page.tsx:98` → `:150` → `:193` |
| `/library` | 2단 | `library/page.tsx:82` → `:99` |
| `/mypage` | 3단 | `mypage/page.tsx:93` → `:99` → `:127` |
| `/book/{id}` | 4단 | `book/[id]/page.tsx:100` → `:117` → `:126` → `:163` |
| `/read` | **6단** | `read/page.tsx:130` → `:144` → `:151` → `:188` → `:214` → `:215` |

여기에 미들웨어의 `auth.getUser()`가 **화면당 1회 더** 붙는다(`middleware.ts:22`).
단계 하나하나가 태평양을 건너므로 **단계 수만큼 지연이 곱해진다.**

단계 수 자체를 줄이는 것은 코드 변경이라 본 ADR의 범위가 아니다(→ 후속 과제).
본 ADR은 **한 단계의 거리**만 줄인다.

## Decision

### D1 — `vercel.json`에 `regions: ["icn1"]`을 단일 지정한다

저장소 루트에 `vercel.json`을 신설한다. 내용은 스키마 선언과 `regions` **두 키뿐**이다.

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "regions": ["icn1"]
}
```

**다른 키를 넣지 않는다.** 빌드 명령·리라이트·헤더는 각각 `package.json`·`next.config.js`
·`middleware.ts`가 이미 정본을 갖고 있고, `vercel.json`에 사본을 만들면 정본이 둘이 된다.

지역을 **하나만** 적는다. Hobby 플랜은 다중 지역을 허용하지 않으며, 다중 지역은 지금 풀려는
문제(DB와의 거리)와도 무관하다 — DB가 서울 한 곳이라 함수가 여러 지역에 흩어지면 서울 밖
인스턴스는 지금과 같은 왕복을 그대로 진다.

### D2 — per-route `preferredRegion`을 쓰지 않는다

같은 효과를 `export const preferredRegion = 'icn1'`로도 낼 수 있으나 채택하지 않는다.

대상이 **11개 라우트**다(P-0 표 3(e) — `force-dynamic` 선언 지점과 같은 집합).
선언을 11곳에 흩으면 ① 새 라우트를 만들 때마다 한 줄을 잊을 수 있고 ② "이 서비스의 실행
지역은 어디인가"라는 질문에 11개 파일을 열어야 답할 수 있다. 설정은 **한 곳에서 한 번**
읽히는 편이 낫다.

`vercel.json`의 `regions`가 프로젝트 전역에 적용되므로 라우트가 늘어도 자동으로 따라온다.

### D3 — edge 라우트는 손대지 않는다

`app/opengraph-image.tsx:26`이 `runtime = 'edge'`인 저장소 유일의 edge 라우트다.
edge는 지역 지정 대상이 아니므로 본 결정의 영향을 받지 않으며, 이를 Node로 바꾸지도 않는다.

`next.config.js:21-23`의 `/home` 308 리다이렉트도 엣지에서 종결돼 함수를 타지 않는다
(P-0 실측: 배포본 20 ms · `X-Vercel-Id`가 2단).

## Consequences

### 적용 범위

- **Node 런타임 전 라우트** — P-0 표 3(e)의 `force-dynamic` 11곳을 포함해 프로젝트의 모든
  서버리스 함수. 미들웨어(`ƒ Middleware 82.1 kB`)도 함께 서울에서 돈다.
- **코드 로직 변경 0건.** 신설 파일 1개와 본 ADR 1개가 전부다.

### 되돌리기

`vercel.json`을 삭제하고 push하면 즉시 원복된다(기본값 `iad1` 복귀). 마이그레이션·데이터
변경이 없으므로 되돌리는 비용이 파일 1개 삭제에 그친다.

### 검증 기준

1. 배포 완료 후 `curl -sI https://www.hellokiki.co.kr/`의 **`X-Vercel-Id` 가운데 토큰이
   `icn1`** 이다(`icn1::iad1::…` → `icn1::icn1::…`).
2. P-0 표 1 **(A)·(C)를 같은 방법으로 재측정**한다 — 같은 책 id
   (`0155f30d-3020-48d8-b39c-4f3c5c48695a`) · 로그인 상태 · 5화면 · 3회 중앙값.
3. 회귀: 6화면이 200을 반환하고 화면이 정상 렌더된다.

### 확인하지 않은 것

- **cold start 빈도**가 지역 변경으로 달라지는지는 재지 않는다. `icn1`은 `iad1`보다 트래픽이
  적어 인스턴스 재사용률이 낮을 수 있으나, 지금 트래픽 규모에서 측정할 표본이 없다.
- **이미지·오디오 자산**의 지연은 바뀌지 않는다. 표지는 외부 호스트(s3·digitallibrary·
  bookdash) 직결이고(`next.config.js:30` `unoptimized: true`) 함수를 타지 않는다.

### 후속 과제 (P-1 이관 — 본 ADR 범위 밖)

본 결정은 **왕복 1회의 거리**만 줄인다. 아래는 왕복 **횟수**와 전송량 쪽이라 별도로 다룬다.

1. **순차 호출 단계 병렬화** — 특히 `/read` 6단(`read/page.tsx:130·144·151·188·214·215`).
2. **Auth 2중 호출** — `middleware.ts:22`와 각 page의 `auth.getUser()`가 화면당 2회.
3. **폰트 preload 90개 현상** — 배포본 HTML이 `as="font"` preload 90개를 내보내 화면당
   woff2 95개·768.9 KB를 받는다. 로컬 제품 모드는 같은 빌드인데 preload 0개·10개·99.6 KB다.
4. **이미지 `unoptimized: true`** — `next.config.js:30`. `/library`가 원본 표지 24장
   (표본 6건 평균 66.3 KB, 건당 638~1,047 ms)을 리사이즈 없이 받는다.
