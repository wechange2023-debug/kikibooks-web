**전환 경로 = 2-B(병행 유지).** 사유 1줄 — RPC가 반환하는 4항목은 집계 수치뿐이고
`readBooks`(최근 완독순 20권)·`favoriteBooks`·`points`는 RPC 밖 데이터라, 4수치만
RPC로 옮기고 목록 경로는 남겼다.

**그 결과 마이페이지의 세션 조회는 이렇게 바뀌었다.**

- **4수치**(완독 종수·읽는 중 종수)는 이제 RPC 하나가 정본이다. 청크 기반 산출은
  **제거**했다 — 같은 수치를 두 경로로 만들지 않는다(정본 이원화 금지).
- **RPC 실패·0행은 기존 `degraded`로 승격**하며 **청크 방식으로 폴백하지 않는다**.
  폴백은 본 ADR이 없앤 절단 버그를 그대로 되살리기 때문이다. 신규 필드 0건.
- 목록용 세션 조회는 남지만 **범위를 완독 세션으로 한정**했다. 절단의 직접 원인이던
  전체 세션 전량 스캔(실측 2,433행)이 사라지고 완독 행(실측 52행)만 읽는다. 이 경로의
  D1 청크 가드는 **유지**한다 — 목록이 조용히 잘리면 '읽은 책'에서 책이 사라진다.

**§D1의 "청크 경로는 D2-b 배포와 함께 제거한다"는 아직 발효하지 않는다.** 그 문장은
D2-b 최종 계약(`get_mypage_summary` — 3수치 + **목록 20권** + P1)을 전제로 쓰였는데,
이번에 배포된 함수는 집계 4수치 전용(`get_child_reading_stats`)이라 목록이 여전히
세션 조회에서 나온다. 목록까지 RPC가 반환하게 되는 시점(O-5 종결 후)에 제거한다.
`lib/shared/row-cap.ts` 자체는 #2·#3이 계속 쓰므로 그때도 남는다.

**SECURITY INVOKER 채택 (결정 근거).** 함수를 호출자 권한으로 실행하면 `reading_sessions`의
기존 RLS(001 §9.4)가 그대로 적용되어 **정책을 새로 쓸 필요 없이** 타인 자녀 데이터 노출 표면이
애초에 생기지 않는다. `SECURITY DEFINER`는 RLS를 우회하므로 함수 안에서 `auth.uid()` 소유권
검증을 직접 해야 하고, **그 한 줄을 빠뜨리면 전 사용자 통계가 열린다** — 이득(계획 최적화)에
비해 실패 비용이 압도적으로 크다. 타협 불가 항목으로 고정한다.

**작성된 RPC의 이름·범위가 D2-b 최종 계약과 다르다.** 파일이 만드는 함수는
`public.get_child_reading_stats(p_child_id uuid)`이며 집계 4수치
(`session_rows` · `completed_titles` · `in_progress_titles` · `last_read_at`)만 반환한다.
목록 20권·P1까지 한 함수로 묶는 `get_mypage_summary`는 **O-5(P1 화면 요구)가 닫힌 뒤**에
확정되므로, 최종 계약명을 미리 점유하지 않았다. 권수 2종은 ADR-0024 O2의 **책 종수** 정의를
그대로 따르며(행 수 기준으로 바꾸는 것은 곧 정의 개정이므로 하지 않는다),
`in_progress_titles`는 완독 종수 집합과의 **차집합**이라 두 수치가 상호 배타다.

## Context

### 1. 증상 — 이미 절단 중이다 (예방이 아니라 시정)

마이페이지(`/mypage`)의 수치 이상 3건을 조사하던 중 발견됐다. `lib/mypage/summary.ts:110-115`의
`reading_sessions` 조회에는 **LIMIT도 `.range()`도 없다**. PostgREST는 상한을 넘는 요청에 오류를
반환하지 않고 **행을 조용히 잘라서** 200으로 응답한다. 잘린 배열은 그대로 카운트 로직에 들어가고,
화면은 축소된 수치를 **정확한 값인 것처럼** 표시한다.

**2026-08-15 Q1 실측** — `scripts/sql/diag/mypage_metrics_diag.sql` 실행(팀장), 자녀 `키키주니어`
(`1eb93951-8a1a-4780-b1a0-6b952a0b92af`):

| 항목 | 실측 |
|---|---|
| `sessions_total` | **2,433** — 통설상의 상한 1,000의 **2.4배** |
| `completed_true` / `completed_false` | 52 / **2,381** |
| `completed_at_null` | 2,381 |
| `distinct_books` / `distinct_books_completed` | **2,397** / 45 |
| `flag_completed_no_ts` / `flag_ts_no_completed` | **0 / 0** |

자녀 6명 분포: 키키주니어 **2,433** · 초은우 45 · 우혀니 32 · kikikiki 4 · Ruthster 2 · Test 1.

**초안의 "975행 · 여유 25"는 틀린 관측이었다.** 그 975는 DB의 실제 행 수가 아니라 **화면이 표시한
숫자**(930 + 45)였고, 그 화면 숫자 자체가 이미 절단의 산물이었다. 임계에 가까운 것이 아니라
**이미 넘은 지 오래다**.

- 화면의 "읽는 중 930"은 실제 값이 아니라 **1,000행으로 잘린 배열에서 계산된 숫자**다. 실제
  미완독 종수는 **2,352권**이며, 화면은 **1,400권 이상을 누락**한 채 정확한 값인 것처럼
  표시해 왔다. (Q2의 `in_progress_books`는 2,381이다. 차이 29는 **완독과 미완독 양쪽에 걸친
  책** — 화면 정의가 "완독한 적 있는 책"을 빼기 때문이다: 45 + 2,381 − 2,397 = 29,
  2,381 − 29 = **2,352**.)
- **"완독 45권"이 실측과 일치하는 것은 조건부 보호의 결과일 뿐 안전의 증거가 아니다.**
  조회가 `.order('completed_at', { ascending: false, nullsFirst: false })`(`summary.ts:114`)로
  정렬하므로 완독 행(52)이 전부 앞쪽 1,000행 안으로 밀려 들어온다. 보호 조건은 단 하나 —
  **완독 행 수 < 상한**이다. 완독이 상한을 넘는 순간 완독 권수도 함께 틀리기 시작한다.
  그리고 이 보호는 **읽는 중 수치에는 전혀 적용되지 않는다**(미완독 행은 전부 뒤로 밀려 잘린다).
  완독 수치만 우연히 멀쩡해 보인 것이 **문제를 지금까지 감춰왔다**.
- 따라서 본 건은 예방이 아니라 **현재 진행 중인 오표시의 시정**이다.

**상한 = 1,000 — 실측 확정.** 2026-08-15 팀장 확인(Supabase **Project Settings → API → Max rows
= 1,000**). 이 값으로 절단을 되짚으면 반환분은 완독 52행 + 미완독 948행이고, 그 948행의 `book_id`
종수가 화면의 **930**과 맞아떨어진다(중복 18행). 관측치 **930과 45가 이 값 하나로 동시에
재현**된다 — 절단이 어떻게 작동했는지의 설명으로 그대로 유효하다.
(이 추론은 실측 **전에** 정황 증거로 먼저 제시됐고, 실측이 같은 값을 확인했다.)

**`flag_completed_no_ts` · `flag_ts_no_completed`가 모두 0**이다 — `is_completed`와 `completed_at`
두 완독 표식이 전 행에서 일치한다. 즉 **데이터 정합성 문제가 아니라 순수한 조회 절단 문제**로
범위가 좁혀진다. 고칠 곳은 데이터가 아니라 조회 방식이다.

**`book_review` 860/1,000 fail-loud 가드에 이은 두 번째 동일 성격 지점**이다. 다만 성질이 반대다 —
`book_review` 쪽은 임계에서 **시끄럽게 실패**하도록 설계됐고, 여기는 **조용히 오답**을 낸다.
그리고 `book_review`는 아직 임계 전이지만, **이쪽은 이미 넘었다**.

### 2. 이 상한이 무엇을 망가뜨리는가

- 완독 권수·읽는 중 권수가 실제보다 **작게** 표시된다(오류 표시 없음). **#1은 가정이 아니라
  현재 상태다** — 읽는 중 수치가 2,352 대신 930으로 표시되고 있다(§1).
- 홈 화면의 "이미 읽은 책 제외" 로직이 잘리면 **완독한 책이 미독으로 재노출**된다(§3 #2·#3).
- 어느 경우에도 로그·예외·사용자 안내가 남지 않는다. 발견은 사람의 눈으로만 가능하다.

### 4. 실측 — 상한값의 출처 (C-2)

**코드·설정 파일에 명시된 상한값은 없다.**

- `supabase/` 하위는 `migrations/`뿐이며 `config.toml`이 **부재**하다.
- `.env.local`·`.env.example`에 `MAX_ROWS`/`PGRST*`/`ROW_LIMIT` 계열 키 **0건**.
- 저장소 전역 검색에서 `max_rows`·`PGRST_DB_MAX_ROWS` 설정 **0건**.

한편 저장소에는 1,000을 전제한 `.range()` 청크 **관행**이 이미 있다.

- `app/showcase/[source]/page.tsx:50` — "Supabase 기본 1000행 cap 때문에 `.range()`로 청크 반복한다"
- `lib/admin/review/query.ts:184` — "`.range(start, start+999)` + `len(rows) < 1000` 종료 조건이
  그 관행의 증거다"
- 파이썬 5종(`verify_licenses.py`·`verify_gdl_sync.py`·`process_tts_requests.py`·
  `run_tts_full708.py`·`tts_targets.py`)이 전부 `.range` 청크 루프.

**이것은 관행의 증거이지 값의 근거가 아니었다.** 위 인용은 전부 우리 코드의 주석·구현일 뿐,
프로젝트에 적용 중인 실제 상한을 확인해 준 적이 없다.

**실값은 2026-08-15 팀장 실측으로 확정됐다 — Supabase Project Settings → API → `Max rows` =
1,000.** 관행이 전제해 온 값과 일치한다. 이로써 §1의 절단 재구성(완독 52 + 미완독 948 → 종수 930)이
추론이 아니라 확정 사실이 되고, D1의 구현 경로도 확정된다(§D1 — `.limit(N)` 판정 불가 →
`.range()` 청크).

## Decision

### D1. 감지 가드를 즉시 넣는다 (C안 — fail-silent → fail-loud)

조회 결과가 상한에 도달했으면 **잘렸을 수 있다**고 판정하고, 수치를 조용히 내보내지 않는다.

**적용 대상 (§3 표 기준)**

| 대상 | 처리 |
|---|---|
| **#1** `lib/mypage/summary.ts` | 기존 `degraded: boolean`(:69, :183)을 **재사용**한다. 신규 필드 0건. 화면(`app/(reader)/mypage/page.tsx:120-122`)이 수치 옆에 정합 불가를 표시한다 |
| **#2** `lib/home/recommendations.ts` | 서버 로그 1줄. 추천은 폴백 사다리가 있어 화면 표시는 바꾸지 않는다 |
| **#3** `lib/home/categories.ts` | 서버 로그 1줄. 동상 |

**#4(`streak.ts`) 비적용** — 이번 주 월요일 이후로 좁혀져 있어 임계 도달이 현실적으로 불가하다.
**자녀 1명 × 당주 월요일 이후 완독분으로 상한이 구조적으로 제한**되기 때문이다(2026-08-18 보강).
불필요한 가드는 넣지 않는다. #5·#6·#7은 구조적으로 안전하다(§3).

**표시 문구는 본 ADR에서 확정하지 않는다.** 제안만 남긴다 — 예: 수치 옆 작은 글씨로
"기록이 많아 일부만 집계했어요", 또는 마이페이지 상단 1줄 안내. 유아 서비스 톤과 부모 대상
정확도 사이의 선택이므로 팀장 결정 사항이다(→ O-3).

**판정 원칙 — (b) 요청 쪽이 임계를 소유한다.** 서버 상한값을 코드에 박제하는 판정((a))은
**반려**한다 — 대시보드 값이 바뀌면 코드가 조용히 틀린다. 임계는 코드가 소유해야 한다.

**구현 확정 — `.range()` 청크. 서버 상한 실측 = 1,000.**
2026-08-15 팀장 확인(Project Settings → API → Max rows = 1,000). 이로써 초안이 권고한
`.limit(N)` + `rows.length === N` 판정은 **성립하지 않는다** — 그 판정은 `서버 상한 > N`일 때만
유효한데, 상한보다 큰 N을 잡을 수 없어 `rows.length === N`이 "잘림"을 뜻하지 못한다.
원칙(임계를 코드가 소유한다)은 유지하고 **구현만 청크 반복으로 확정**한다. 청크도 크기와 종료
조건을 코드가 소유하므로 원칙에 어긋나지 않는다. (초안의 `N = 2000`·`N = 5000`은 모두 폐기.)

- 청크 크기 **1,000**으로 반복 조회하고, 반환 행이 **1,000 미만이면 종료**한다.
  `lib/admin/review/query.ts:184` · `app/showcase/[source]/page.tsx:56-79`의 **기존 관행과 동일한
  패턴**을 쓴다 — 새 패턴을 만들지 않는다.
- **fail-loud 성격은 유지한다.** 청크 반복은 전량을 정확히 받지만, 왕복 수가 일정 임계
  (예: **5왕복 = 5,000행**)를 넘으면 서버 로그로 경고를 남긴다. D2-b 배포 전까지의 감시 장치다.
- 청크 경로는 **임시 안전장치**이며 **D2-b 배포와 함께 제거**한다(§Alternatives A1 반려 범위).

### D2. 집계를 DB로 이관한다 (B안 — 본작업). **확정: D2-b(RPC)**

애플리케이션이 세션 행을 전량 받아 JS로 세는 구조를 폐기하고, **DB가 집계한 결과만** 받는다.
행 수와 무관하게 왕복 1회로 고정되며 상한 문제 자체가 소멸한다. ADR-0024 O2의 **권수 정의
(책 종수)는 그대로**이며 산출 위치만 옮긴다.

**확정 — D2-b. RPC `get_mypage_summary(child_id uuid)`.** 근거 3가지:

- **P1(이어읽기·배지·더보기)이 전부 같은 세션 데이터를 읽고, 전부 마이페이지 한 화면에 놓인다.**
  D2-a(뷰)는 카운트만 주므로 목록·이어읽기가 별도 조회로 남아 **화면 하나가 3~4개 경로에서**
  데이터를 받게 된다. D2-c(혼합)는 그 분산이 더 크다.
- **D2-b는 함수 하나가 화면 전체의 정합을 보증한다.** 3수치·목록 20권·P1 요소가 같은 조회에서
  나오므로 항목 간 어긋남이 구조적으로 생기지 않는다. ③(완독 45권인데 목록 16권 표시)도
  부수적으로 함께 닫힌다.
- **D2-b의 단점("시그니처가 화면 계약이 되어 이후 변경이 무겁다")은 뒤집으면 P1 요구를 먼저
  확정해야 한다는 뜻이다.** 이를 회피하지 않고 실행 순서에 단계로 신설해 흡수한다
  (§실행 순서 3단계 — P1 화면 요구 확정이 RPC 시그니처의 입력이 된다).

D2-a·D2-c는 **반려**하며 사유는 §Alternatives **A3·A4**에 남긴다. 아래 비교표는 그 판단의
근거로 유지한다.

| 안 | 형태 | 장점 | 단점 |
|---|---|---|---|
| **D2-a** | **뷰** `child_reading_stats`(자녀 1행 = 완독 종수·읽는 중 종수) | 선언적이라 로직이 SQL 한 곳에 모인다. PostgREST가 자동 노출 → 호출부는 `.from(...).eq('child_id', …).maybeSingle()` 1줄. 마이그레이션이 짧다 | 파라미터를 못 받아 **전 자녀 집계 후 필터** 형태다. 인덱스(`idx_reading_sessions_child_id`)를 타는지 실행계획 확인이 필요하다. 목록 20권은 별도 조회로 남는다 |
| **D2-b** | **RPC** `get_mypage_summary(child_id uuid)` | 파라미터를 받아 해당 자녀만 집계한다. **3수치 + 목록 20권을 한 번에** 반환해 화면 정합을 함수 하나가 보증한다(③ 목록 불일치도 같이 닫힌다) | 반환 타입 정의가 필요해 마이그레이션이 길다. 함수 시그니처가 화면 계약이 되어 이후 변경이 무거워진다 |
| **D2-c** | 혼합 — 카운트만 뷰/RPC, 목록 20권은 현행 유지 | 변경 표면이 가장 좁다. 위험 지점(#1의 무한정 조회)만 정확히 제거한다 | 화면 하나가 두 경로에서 데이터를 받는다. 목록 쪽 상한 노출은 남는다(단, 20권 슬라이스라 실질 위험 없음) |

**RLS 설계 (D2-b 기준)**

- **`security invoker`로 만든다.** 함수가 **호출자 권한으로** 실행되면 `reading_sessions`의 기존 RLS
  (001 §9.4 `parent_id = auth.uid()` 계열)가 그대로 적용된다. 정책을 새로 쓸 필요가 없고,
  "남의 자녀 통계가 보이는" 사고의 표면이 생기지 않는다. PostgreSQL 함수는 **기본값이 INVOKER**
  이므로 선언 없이도 성립하나, 의도를 드러내기 위해 마이그레이션에 명시한다.
- **`security definer`는 쓰지 않는다.** RLS를 우회하므로 함수 내부에서 `auth.uid()`로 소유권을
  직접 검증해야 하고, 그 검증을 한 줄 빠뜨리면 **전 사용자 통계가 열린다**. 이득(계획 최적화)에
  비해 실패 비용이 크다.
- **근거 소멸 1건 — 처분 완료**: 초안의 "뷰 `security_invoker = on`은 PostgreSQL 15 이상" 의존은
  **D2-a 반려로 소멸**했다(함수는 그 제약을 받지 않는다). 이에 따라 PG 메이저 버전 확인 항목은
  **삭제**했고, 남은 실측 항목이던 상한 실값도 2026-08-15에 확인돼(= 1,000) **팀장 실측 대기
  항목은 0건**이다.

**실행 주체**: 함수 신설은 DB 오브젝트이므로 `supabase/migrations/` 파일로 일원화하고
(ADR-0046 D5) **실행은 팀장의 SQL Editor**가 한다. 워커는 마이그레이션 파일과 호출부 코드까지다.

### D3. 순서 — D1이 먼저, D2가 본작업

D1은 정확도를 고치지 않는다. **잘린 수치를 정확한 척 보여주는 상태를 끝내는 것**이 목적이며,
D2가 배포될 때까지의 안전장치다. D2 완료 후 D1의 가드는 남긴다 — 비용이 0에 가깝고,
이후 다른 조회가 같은 함정에 빠지는 것을 계속 잡아준다.

## Alternatives

### A1. `.range()` 청크 반복 — 반려

`app/showcase/[source]/page.tsx:56-79` 선례를 복제해 2,433행을 3왕복으로 나눠 받는다.

- 장점: 사내 선례가 있어 패턴 논쟁이 없다. DB 변경 0건이라 ADR 없이도 처리 가능하다.
- **반려 사유**: 상한을 **미룰 뿐** 없애지 못한다. 근본적으로 렌더마다 전량 스캔(O(n))이며,
  마이페이지는 자주 도는 화면이라 왕복 누적이 그대로 체감된다. 실측 2,433행이면 이미
  **3왕복**이고, 미완독이 계속 쌓이므로 왕복 수는 단조 증가한다. 무엇보다 §3의 비대칭 때문에
  #1만 고쳐도 세션 증식이 계속되면 #2·#3이 다음 차례다. 조회 방식 자체를 바꾸지 않으면
  같은 처치를 지점마다 반복하게 된다.
- **반려 범위는 D2 본작업 한정이다.** D1의 안전장치로 쓰는 `.range()` 청크는 여기서 반려하지
  않는다 — 서버 상한이 **1,000으로 확인됐으므로** `.limit(N)` 판정이 성립하지 않고
  **D1은 청크 경로로 확정**됐다(§D1). 그 청크는 "전량을 정확히 받기 위한 임시 안전장치"이지
  "집계 방식의 최종 해답"이 아니며, D2-b 배포와 함께 사라진다.

### A2. 대시보드 Max rows 상향 — 반려

- 장점: 코드 변경 0건.
- **반려 사유**: fail-silent 성질이 **그대로 남는다** — 임계만 옮길 뿐 잘릴 때 여전히 조용하다.
  게다가 전 테이블·전 API에 전역 적용되어 영향 범위를 통제할 수 없고, 다음 임계에서 더 큰
  규모로 재발한다.

### A3. D2-a — 뷰 `child_reading_stats` — 반려

자녀 1행(완독 종수·읽는 중 종수)을 내는 뷰를 만들고 화면이 그것만 읽는다.

- 장점: 선언적이고 마이그레이션이 짧다. 호출부가 1줄로 줄어든다.
- **반려 사유**: **카운트만 준다.** 목록 20권과 P1(이어읽기·배지·더보기)이 별도 조회로 남아
  **화면 하나가 3~4개 경로에서** 데이터를 받게 되고, 경로마다 정합을 따로 보증해야 한다.
  ③(완독 45권인데 목록 16권)처럼 **항목 간 어긋남**이 바로 그 분산에서 나온 증상이라,
  분산을 유지하는 안은 같은 증상을 다시 부른다. 파라미터를 못 받아 전 자녀 집계 후 필터가
  되는 점도 부수적 부담이다.

### A4. D2-c — 혼합(카운트만 DB, 목록은 현행) — 반려

- 장점: 변경 표면이 가장 좁고, 위험 지점(#1의 무한정 조회)만 정확히 제거한다.
- **반려 사유**: A3의 분산 문제를 **더 크게** 안는다 — 카운트·목록·P1이 각각 다른 경로가 된다.
  변경 표면이 좁다는 장점은 P1이 붙는 순간 사라진다(같은 세션 데이터를 읽는 지점이 3개 더
  생긴다). 지금 좁게 고치고 P1에서 다시 고치는 2회 작업이 된다.

## Non-goals

- **세션 증식 정책의 변경은 본 ADR 범위 밖이다 — 단, 별도 트랙 · 우선순위 높음.**
  `startReadingSession`이 리더 진입마다 미완독 세션을 INSERT하고(중복 가드 키가
  `completed_at IS NULL`뿐) 완독 후 재진입 시 새 행이 생기는 구조 자체는 **별도 트랙**으로
  분리한다. 다만 "언젠가 볼 문제"가 아니다 — 자녀 1명의 미완독 **2,381행**(2,397권 열람)은
  정상 사용 패턴으로 설명되지 않으며, **절단의 직접 원인**이다. 본 ADR의 D1·D2가 증상을
  가리는 것을 멈추게 할 뿐, 원인은 이 트랙에서만 사라진다.
  진단 SQL **Q2(미완독 세션의 시간 분포)는 우선순위 판단 자료가 아니라 정리 방식 —
  일괄 삭제 대상 선별 기준 — 을 정하는 자료**다. 본 ADR은 "이미 쌓인 행을 어떻게 안전하게
  셀 것인가"만 다룬다.
  - **유력 가설 — 미완독 2,381행은 아이의 독서 기록이 아니라 관리자 검수 열람의 흔적이다.**
    팀장 증언: 2026-07 중순~08 초에 **서비스 가능 도서 선별을 위해 사람이 대부분의 도서를 직접
    열어봤고, 그때 쓴 계정이 키키주니어**다. **Q2 실측이 부합한다** — `in_progress_rows` 2,381 =
    `in_progress_books` 2,381(**중복 0** — 책마다 정확히 1회 열람), `d_7_30` **2,298(96.5%)** ·
    `d_0_7` 6 · `d_30_plus` 77, `oldest` 2026-05-29 · `newest` 2026-08-14. 96.5%가 몰린 구간이
    증언한 기간과 일치한다.
  - **원인 확정(2026-08-15 코드 실측).** 관리자 도서 목록의 썸네일이 **사용자용 리더 라우트를
    그대로 연다** — `components/admin/books/admin-books-browser.tsx:199-202`(`/book/{id}/read`를
    새 탭으로). 같은 파일 주석 `:160-164`가 "admin 전용 뷰어 0건 — 운영자와 사용자가 같은 화면을
    본다(검수 신뢰성)"을 의도로 박제하고 있다. 세션 INSERT는 `lib/book/reading-session.ts:118-122`
    **한 곳뿐**이며 리더 3종(html·audio·asb)의 마운트 `useEffect`가 이를 부른다. 도입 커밋은
    **`5bd84c8`(2026-07-28)** 로 Q2의 `d_7_30` 구간과 일치한다. 따라서 이것은 데이터 오염이 아니라
    **구조적 결함**이며, **정리만으로는 재발한다**.
  - **가설이 맞아도 D1·D2는 취소하지 않는다.** 맞다면 2,381행은 거의 전량 삭제 대상이고,
    삭제하면 세션이 약 52행으로 줄어 **절단은 즉시 소멸**한다. 그러나 정리는 **일회성**이다 —
    다음 선별 작업에서 동일하게 재발하고, 실사용자가 늘면 같은 임계를 다시 만난다.
    **정리는 시간을 벌 뿐 구조를 고치지 않는다.**
  - **재발 방지 — 관리자 열람이 세션을 만들지 않게 하는 구조 — 는 이 트랙의 일부다.**

    도서 탈락의 **2중 축소**이며, **D2-b가 목록까지 한 함수로 반환하면 함께 닫힌다**(§D2).

  - **가설 확정** — 커밋 `a4c56cc`(2026-08-14) "관리자 검수 열람이 독서 기록을 남기지 않도록
    preview 가드 추가". `lib/book/preview-mode.ts`가 원인(관리자 도서 목록 썸네일이
    `/book/{id}/read`를 그대로 여는 커밋 `5bd84c8`, 2026-07-28)과 2중 방어(리더 3종의
    `usePreviewEntry` + `startReadingSession`의 관리자 AND preview 확인)를 박제한다.
    가설이 확정되지 않았다면 재발 방지 구조를 만들지 않는다.
  - **삭제 대상 선별 기준** — 커밋 `f7b268c`(2026-08-14)
    `scripts/sql/cleanup/purge_admin_preview_sessions.sql`이 **기준 B**(해당 자녀 AND 미완독
    AND `started_at` 7일 초과)를 A안(미완독 전량)·C안(전 자녀 30일 초과) 대비 사유와 함께
    확정했다. 완독 52행 보존을 `is_completed = false`로 명시 보장한다.
  - **범위 한정** — 본 종결은 O-4가 요구한 위 2건에 한정된다. 정리 SQL의 **실제 실행 여부는
    O-4의 요건이 아니며**(팀장 소관, ROLLBACK 종료 상태) 별건으로 남는다.
  - 처음부터 **D1·D2의 우선순위와 내용은 이 조사 결과와 무관하게 확정**이었고, 그 판단은
    바뀌지 않았다.
- **O-5**: **P1(이어읽기·배지·더보기)의 화면 요구가 RPC 반환 형태를 정한다.** 함수가 무엇을
  돌려줘야 하는지는 P1 요구가 확정돼야 정해진다 — 실행 순서 3단계가 그 의존을 처리한다.
  (D2 방식 자체는 D2-b로 확정됐으므로 더 이상 열린 문제가 아니다.)
- **O-6**: **다자녀 — 화면이 어느 자녀를 표시하는가**(선택 규칙은 코드 실측으로 확정, 처분만 열림).
  단일 진입점은 `getActiveChild`(`lib/home/active-child.ts:47-64`)이며 규칙은 **`children`에서
  `parent_id = 로그인 사용자` 필터 후 `created_at ASC LIMIT 1`** — 즉 **그 학부모가 가장 먼저
  만든 자녀 1명**이다. 마이페이지도 이 함수를 그대로 쓰고(`app/(reader)/mypage/page.tsx:81`),
  주석 :31이 "베타는 활성 자녀 1명 기준 … 자녀 선택 UI는 정식 단계 보류"로 박제하고 있다
  (ADR-0024 D8). **전환 UI는 코드에 존재하지 않는다** — 추정이 아니라 실측이다.
  - **`children` 실측(Q5): 총 10명.** 세션 보유 6명(키키주니어 2,433 · 초은우 45 · 우혀니 32 ·
    kikikiki 4 · Ruthster 2 · Test 1) + **세션 0인 4명**(Lala · 훌 · test kiki · 테스트 키키).
  - 따라서 10명이 한 화면에서 전환되며 보이는 것이 아니라, **로그인 계정마다 고정된 1명**이
    보인다. 10명이 어느 부모에 어떻게 묶이는지는 **Q1·Q5 산출물에 `parent_id`가 없어 아직
    확인되지 않았다** — `scripts/sql/diag/session_origin_diag.sql` **R6**가 이를 닫는다.
  - 테스트로 보이는 자녀(`Test` · `test kiki` · `테스트 키키` · `Ruthster` · `kikikiki` 등) 정리
    여부는 **팀장 판단**으로 남긴다. 본 ADR의 결정에는 영향이 없다.
- **O-7**: **Closed (2026-08-18) — 적립 로직 정상. 버그 아님.**
  진단 조회 `scripts/sql/o7_points_diag.sql`(R1~R4, 조회 전용)을 팀장이 실행한 실측으로 종결.
  - **실측(2026-08-18 팀장 실행)** — 자녀별 완독 세션 행수와 그에 따른 기대 포인트:

    | 자녀 | `completed_rows` | 기대 포인트(= ×50) | `completed_titles` |
    |---|---|---|---|
    | 키키주니어 | 52 | 2,600 | 45 |
    | 초은우 | 17 | 850 | 13 |
    | 우허니 | 16 | 800 | 15 |
    | kikikiki | 1 | 50 | 1 |

  - **원래 의문("완독 45권인데 2,650P")은 단위 오해였다.** 포인트는 완독 **세션 행수**
    기준이고(`lib/book/rewards.ts:112-117`, ADR-0018 D5 "매 완독 +50"), 화면의 "완독"은
    ADR-0024 O2의 **책 종수** 기준이다. 같은 책을 재완독하면 행수만 늘고 종수는 그대로이므로
    **두 값이 일치하지 않는 것이 설계**다. 45 × 50 = 2,250과 비교한 것 자체가 단위 착오였다.
  - **잔여 +50**(키키주니어 2,650 − 2,600)은 적립 로직이 아니라 **화면 표시 계층의 자녀 매핑
    문제로 분류**하고 마이페이지 **P1 트랙으로 이관**한다. ★ **이 잔여분의 원인은 확정되지
    않았다** — "P1에서 확인할 항목"이며 단정하지 않는다.
  - **근거의 한계(기록 보존)**: 팀장이 회신한 실측 표에 `points`·`diff_vs_rows` 열이 포함되지
    않아, 워커는 "4명 전원 정합"을 로컬에서 재검산하지 못했다. 위 표의 기대 포인트는
    `completed_rows × 50`으로 워커가 산출한 값이고, 정합 판정과 잔여 +50은 팀장 판정을 인용한
    것이다. 원문이 기록한 **초은우 −50**의 현재 해소 여부도 이번 회신에 증거가 없다.
    P1 트랙에서 잔여분을 볼 때 함께 확인할 것.

  아래는 종결 전까지의 기존 기록이다(보존).
- **O-7 (원문)**: **포인트 적립 경로 밖의 증감이 존재한다**(Q5 실측). `children.points`가 완독 세션 수
  × 50과 어긋난다 — **키키주니어 +50**(2,650 vs 52세션×50 = 2,600) · **쵸은우 −50**(800 vs
  17세션×50 = 850). 우혀니(800 / 16세션)와 kikikiki(50 / 1세션)는 **차이 0**이다.

  움직였다는 뜻이다. +50과 −50의 대칭이 눈에 띄나 **단정하지 않는다** — 자녀 간 오귀속
  가능성이 있어 방치하지 않는다. 규모는 총 100P로 작고 테스트 성격 계정 위주라 **비차단**이다.
  **원인 조사는 별도 트랙**이며, **본 ADR의 D1·D2에는 영향이 없다** — 조회 절단과 무관한
  **쓰기 경로** 문제다.
  - 초안(§Non-goals ②)의 판정 "`diff_by_session`이 0이면 정의 차이일 뿐"은 **전제가 무너졌다**.
    0이 아닌 자녀가 2명이다.
