# Book Dash 세로(long-scroll) 형식 도서 정찰 — TTS 실행 전 영향 범위

작성 2026-07-27 · 기준 HEAD `ca8a884` · **읽기 전용**(이미지 변환·업로드·DB 쓰기·Polly 호출 0건)
계측 스크립트: `scripts/pdf_harvest/audit_aspect.py`

## 요약 (먼저 읽을 3줄)

1. **세로로 긴 이미지는 book_dash 어디에도 없다.** Storage `book-images` 전 201폴더 실측 결과
   최대 h/w = **1.05**(거의 정사각)이고, 임계 2.0은커녕 1.5를 넘는 이미지가 **0장**이다.
2. 팀장이 보신 "세로로 길게 이어진 형식"은 이미지가 아니라 **`content_type='html'` 54권**일
   가능성이 높다. 이들은 `bookdash.github.io` 외부 HTML을 **iframe으로 임베드**하며, 그 원본
   페이지가 세로 스크롤 문서다. **이 54권은 TTS 116권에 한 권도 포함되지 않는다**(텍스트 없음으로 이미 제외).
3. 다만 **분할 위험 자체는 실재한다.** TTS 116권의 이미지는 전부 **1600×800 (2:1) 2면 스프레드**다.
   이걸 좌/우로 잘라 가로 슬라이드로 만들면 **116권 전부 페이지 번호가 바뀐다.**

## Task 1. 세로 형식 도서 식별

### 1-1. 계측 범위와 방법

| 원천 | 범위 | 측정 |
|---|---|---|
| 로컬 렌더 `out_images_154/` | 152권 | 2,128장 **전수** |
| Storage `book-images/book_dash-*` | **201폴더 전체** | 권당 5장 표본 = 965장 |

로컬본과 Storage본이 같은 원천인지 12권 표본으로 치수 대조 → **12/12 일치**(불일치·오류 0).

### 1-2. 실측 분포 (h/w = 세로÷가로)

**로컬 152권 / 2,128장 전수**

| 값 | |
|---|---|
| 중앙값 | 0.5000 |
| 최소 ~ 최대 | 0.5 ~ 1.0 |
| h/w ≥ 1.5 | **0장** |

해상도가 사실상 두 종류뿐이다.

| 해상도 | 장수 | 정체 |
|---|---|---|
| **1600×800** (h/w 0.5) | 1,976 | 본문 **2면 스프레드** — 권당 13장 |
| **1600×1600** (h/w 1.0) | 152 | 각 권 **14번째(마지막) 면** — 정사각 뒤표지 |

152권 × (13 + 1) = 2,128로 **전 권이 동일 구조**다.

**Storage 201폴더 / 965장 표본**: 최소 0.5 · 최대 **1.0477** · h/w ≥ 2.0 **0권**.

### 1-3. 판별 기준에 대한 판단

지시서가 제안한 **h/w ≥ 2.0** 기준으로는 후보가 **0권**이다. 기준을 낮춰도 결과는 같다 —
**전 코퍼스 최대값이 1.05**라서 1.5로 낮춰도, 1.1로 낮춰도 후보는 0권이다.
즉 임계 조정의 문제가 아니라 **세로로 긴 이미지 자체가 존재하지 않는다.**

실제 데이터는 반대 방향으로 치우쳐 있다: 통상 페이지(약 1.4)가 아니라 **가로로 2배 긴 스프레드**(0.5)가 표준이다.

### 1-4. 그럼 팀장이 보신 것은 무엇인가 — 유력 후보

`book_dash` 209권은 렌더 경로가 두 갈래다(`app/(reader)/book/[id]/read/page.tsx:193`).

| content_type | 권수 | 렌더 방식 | 화면 형태 |
|---|---|---|---|
| `html` | **54** | `HtmlReader` → **bookdash.github.io iframe** | 외부 HTML **세로 스크롤 문서** ← 유력 |
| `asb_native` | 155 | `AsbReader` 자체 렌더 | 페이지 단위 가로 슬라이드 |

`html` 54권은 우리 이미지를 쓰지 않고 원본 사이트 페이지를 그대로 띄운다. 세로로 길게 이어져
보이는 화면은 여기서 나올 수밖에 없다. **확인용 URL 54건 전체**: `scripts/pdf_harvest/longscroll_check_urls.csv`

## Task 2. TTS 116권과의 교집합

### 2-1. 교집합

| 기준 | 교집합 |
|---|---|
| 세로 긴 이미지(h/w ≥ 2.0) 보유 권 | **0권** |
| `content_type='html'` 54권 | **0권** — 전원 `book_text` 없음으로 이미 제외됨 |

**어느 해석으로도 TTS 116권에는 세로 형식 도서가 없다.**

### 2-2. book_text 페이지 수 vs 이미지 수

116권 **전건** 대조 결과:

| 관계 | 권수 | 지시서 해석 |
|---|---|---|
| `book_text` 행 **>** 이미지 수 | **0권** | (텍스트가 이미 분할 단위) |
| **1 : 1 일치** | **116권** | **이미지 분할 시 페이지 번호 변경 위험** |
| 이미지 수 > `book_text` 행 | 0권 | — |

로컬 이미지 폴더 누락 0권. 즉 **116권 전부가 1:1**이며, `book_text` 1행 = 1600×800 스프레드 1장이다.

### 2-3. 판정표

| 판정 | 권수 | 근거 |
|---|---|---|
| 안전(텍스트가 이미 분할 단위) | **0** | 해당 없음 |
| **위험(분할 시 번호 변경)** | **116** | 전권 1:1. 스프레드를 좌/우로 자르면 14면 → 27면으로 늘어 `pNN`·`page_index` 전면 재배치 |
| 판단 불가(사람 눈 필요) | 0 (TTS 대상 내) / **54** (html형, TTS 대상 밖) | 아래 2-4 |

### 2-4. 분할이 번호 문제로 끝나지 않는 이유 — 텍스트도 쪼개진다

`book_text.blocks`의 bbox를 권별 스프레드 폭 중앙선 기준으로 판정했다(116권 전건):

| 항목 | 값 |
|---|---|
| 좌·우 **양쪽**에 텍스트가 놓인 면을 가진 권 | **82 / 116권** |
| 텍스트 있는 1,348면 중 양쪽 배치 면 | **328면 (24.3%)** |
| 중앙선을 **가로지르는** 텍스트 블록 보유 권 | **16권 / 65면 (4.8%)** |

- 328면은 분할 시 한 `book_text` 행의 텍스트를 **두 페이지로 나눠 재적재**해야 한다.
  번호만 밀리는 게 아니라 **텍스트 레코드 자체가 쪼개진다** → mp3·marks·`book_audio` 행도 함께 재생성 대상.
- 65면(16권)은 블록 하나가 중앙선을 걸쳐 있어 **기계적 분할이 불가능**하다. 사람 판단이 필요하다.
  대표: `lets-go-on-a-litter-hunt`(2면) 외 15권 — 전체 목록은 재실행으로 산출 가능.

## Task 3. 결론과 권고

### 결론

1. **TTS 116권에 세로 형식 도서는 0권**이다. 팀장이 보신 형식은 `html` 54권(iframe)일 가능성이 높고,
   그 54권은 TTS 대상이 아니다 → **세로 형식을 이유로 TTS를 미룰 근거는 없다.**
2. 그러나 **스프레드 분할 계획을 116권에 적용한다면 이야기가 다르다.** 116권 전부가 1:1이라
   분할 시 페이지 번호가 전면 변경되고, 82권은 텍스트 재적재까지 필요하다.
   **분할 계획이 116권을 포함한다면 TTS는 분할 이후로 미뤄야 한다.**

### 팀장 확인 요청 (1건)

> `scripts/pdf_harvest/longscroll_check_urls.csv`의 뷰어 URL로 확인 가능합니다.
>
> - **예 → TTS 116권과 무관.** 예정대로 진행 가능(54권은 별도 트랙).

>   먼저 끝내야 mp3·`book_audio`를 두 번 만들지 않는다.
